# Code review 1: `stock_pulse/lib` and `market_server/lib`

Reviewer: `reviewer` · 8 Nov 2026 · read-only review of the working tree (another developer was fixing tests at the same time).
Style: **App-layer** (controllers + immutable state in `application/`, manual Riverpod 3 providers, hand-written immutable classes, as the user chose).
Rules applied: `docs/team/build-brief.md`, `docs/10-change-request-2.md` (CR-2), `flutter-code-review` (C/P/U/A/X/Q/T) and `flutter-architecture-review` (L/S/R/E/D/N/T) rule IDs.

Checks: `flutter analyze --fatal-infos lib` ✅ clean · `dart format` ❌ 1 file · `dart analyze market_server/lib` ❌ 11 infos (fails `--fatal-infos`) · tests not run (being fixed in parallel).

## Summary

The structure mostly follows CR-2: `di/` folders exist, `AppRoute` is sealed with typed routes, screens and widgets are split, no raw `Icons.`, no `showSnackBar` outside `FeedbackHost`, and no `*_routes.dart` files are left. Socket, repository and controller code handles async gaps carefully (`ref.mounted`, request counters, generations).

The biggest risk is a **real order-size bug**: the full-screen order ticket multiplies by the lot size twice, so an option ticket from the chain opens at 75 lots instead of 1. Beyond that:

- **Rebuild performance on ticking data:** four screens watch whole live states (order ticket, portfolio, chain, AI chat).
- **CR-2 #9 (responsive layout) is not built:** no breakpoints module and no two-pane layouts.
- **Business logic sits in the order sheet widget,** and that file is over 300 lines.
- **The server can leak half-open WebSocket sessions.**
- **Rule gaps:** about 34 comments cite docs or stories, there are 13 dead files, providers live outside `di/`, and three API paths are still raw strings.

Counts: **Critical 1 · High 8 · Medium 24 · Low 20** (53 rows).

## Questions

- `OrderTicketController` is a non-autoDispose family keyed by symbol, so one instance stays alive per symbol ever traded. That is intended (to keep the uncertain key), but should it be evicted after success?
- In Riverpod 3, is a `Notifier` instance reused when `build` re-runs? If it is, `FeedbackController` closes `_replies` on every rebuild, for example when `clockProvider` changes, and later `actionTapped` would throw. Please confirm with a test.

## Good practices seen

- Async discipline is consistent: request counters in `StockDetailController._loadChart` and `PortfolioController._onOrderUpdate`, generations in `MarketSocket`, and `ref.mounted` after most awaits.
- Per-row `select` in `QuoteTile` and the section `select`s on the stock page keep ticks from rebuilding the whole watchlist or stock page.
- Snackbars are centralised: one `FeedbackHost`, with priority, dedupe window and announcements. There are no `showSnackBar` calls elsewhere.
